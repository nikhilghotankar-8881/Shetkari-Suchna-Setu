# encryption.md — Encryption & Security Controls (what we acquire/use)

Scope honest: we **use managed/standard crypto**. We do not invent crypto. No claim of end-to-end encryption.

## Acquisition list (what we get, from where)
| Need | What we acquire | Source | Cost | Owner |
|------|-----------------|--------|------|-------|
| Transport encryption | TLS certificate (auto-renew) | Host-managed (Vercel/Render) or Let's Encrypt | Free | Infra |
| Domain | Domain/subdomain for HTTPS + HSTS | Registrar / host subdomain | Low/free | Infra |
| DB encryption at rest | Managed Postgres with disk encryption (AES-256) | Supabase / cloud provider | In plan | Infra |
| Backup encryption | Provider encrypted backups | Same | In plan | Infra |
| Secrets storage | Host env-var secrets / secret manager | Render/Railway/Fly/Vercel | Free | Backend |
| Password hashing | Argon2id/bcrypt via auth provider | Supabase Auth / fastapi-users | Free | Backend |
| Token signing key | HS256/RS256 JWT secret/keypair | Generated by us, stored as secret | Free | Backend |
| App-level field encryption (later) | AES-256-GCM lib + key (KMS if available) | `cryptography` lib; cloud KMS | Free/low | Backend |
| Web Push keys (later) | VAPID keypair | Generated by us | Free | Backend |
| Dependency scanning | `pip-audit`, `npm audit`, Dependabot | GitHub | Free | All |

## In transit
- HTTPS everywhere. Redirect HTTP → HTTPS. HSTS on.
- TLS 1.2 min, 1.3 preferred (host default). 
- API ↔ DB: TLS (`sslmode=require`/`verify-full`).
- API ↔ LLM vendor: HTTPS only; public notice text only.
- Security headers: CSP, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`.
- Cookies: `Secure`, `HttpOnly`, `SameSite`.

## At rest
| Data | Protection |
|------|-----------|
| Whole DB + backups | Provider disk encryption (AES-256). **Protects stolen disk/backup, NOT a compromised app or SQL injection.** |
| Profile token | Store SHA-256 hash only |
| Admin passwords | Argon2id/bcrypt (provider) |
| Phone numbers (post-MVP) | AES-256-GCM field encryption, per-record nonce, key from KMS/secret; plus HMAC-SHA256 blind index for lookup |
| Raw notice snapshots | Public data; no extra encryption needed. Integrity: store content hash |
| Secrets | Never in repo/frontend bundle |

## Keys & secrets
- `.env` in `.gitignore`. Secret scan in CI (gitleaks/GitHub secret scanning).
- Separate keys per environment (dev ≠ prod).
- Rotation plan: JWT key + DB password + API keys. Document steps. Rotate if leaked.
- Supabase service-role key = server only. Anon key in frontend is OK only with RLS on.
- Least privilege DB user for API (no superuser).

## Integrity (not same as encryption — we need it)
- Content hash per snapshot → tamper-evident trail of what source said when.
- Audit log append-only (no update/delete grant to app role).

## What encryption does NOT fix (be honest at demo)
- Wrong extracted deadline → verification problem, not crypto.
- Compromised admin account → MFA + RBAC problem.
- Prompt injection in notice → input-handling problem.
- Server-side admin can read profile data (we do not offer E2EE; not needed, data low-sensitivity).

## Decision on app-level encryption for MVP
Counter-argument: "Encrypt every field ourselves." Cost: key mgmt complexity, deadline risk, little gain while stored data is district+crop. **Decision: skip for MVP; require it before any phone/PII field added.** Trigger rule: any new High-sensitivity field in privacy.md → field encryption mandatory first.
